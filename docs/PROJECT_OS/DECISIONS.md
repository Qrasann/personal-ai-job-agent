# Decisions

## 2026-10-20 — Web GUI frozen indefinitely (superseding execution priority)

**Owner instruction:** Freeze Web GUI development for an **indefinite** period. Only an explicit later owner instruction can lift this freeze; completion of milestones, release readiness, test status or passage of time cannot.

- **Do not** add Web GUI features, redesign it, improve its UX, run new rollout initiatives or schedule Web-only owner acceptance.
- **Preserve** existing implementation, tests, artifacts, data and documented evidence; no deletion or rewrite.
- **Exception:** narrowly scoped critical security, compatibility or data-integrity fixes required to protect existing behavior, without new product scope.
- **Telegram is the primary active UI.** Continue approved Telegram UX, vacancy watchers, worldwide relocation, Candidate Facts, Resume/Application/Recruiter/Interview Agents and other agreed roadmap capabilities.
- **Telegram Mini App is deferred separately** and must not be automatically started in place of Web GUI.
- **Decision precedence:** overrides the earlier DEC-011 Web-GUI-primary role and the Web-GUI-first rollout sequence in DEC-015. Retain those records as historical decisions, not active instructions. The shared-data product vision and all unrelated owner approvals remain intact.
- No code, runtime, production database or deployment change is authorized by this decision alone.

## 2026-10-14 — no raw network exception payloads in logs

Telegram startup and HH chat poll diagnostics report exception class and
retry behavior without logging untrusted URL or response text.

## 2026-10-14 — patched dependency minimums

Set minimum pypdf 6.20.1 and python-multipart 0.0.31 based on upstream
security advisories. This keeps compatible newer releases within the existing
major-version policy; reproducible locking needs a separate reviewed process.

## 2026-10-14 — EURES partial failure contract

Search queries and detail IDs are independent EURES work units. A single HTTP
status or malformed response does not discard results from another unit. If
all searches or all attempted details fail, the source reports an error.
Transport retries remain bounded; HTTP statuses are not retried here.

## 2026-10-14 — bounded Job Bank detail cache

Job Bank listing discovery remains fresh on normal source-cache expiry. Detail
HTML for an ID still present in that listing may be reused for one hour in a
256-entry in-memory cache. Manual force refresh bypasses detail cache. The
documented five-second crawl interval remains unchanged.

## 2026-10-14 — fixed source host for Georgia details

Listing HTML is untrusted input. HR.ge/JOBS.GE detail requests accept only
HTTPS URLs on the source host and standard port. Any new HTML detail adapter
must enforce its own source boundary before network fetches.

## 2026-10-14 — one-time resume import confirmation

The pending import preview is claimed before its first persistence operation to
prevent two Telegram callbacks from writing it concurrently. A failed claimed
preview is re-created by resending the file; atomic resume/fact persistence
requires a separate repository transaction design.

## 2026-10-14 — scoped reliability and security boundaries

Candidate Telegram commands and callbacks are private-chat actions; selected
Bot API channel posts retain their separate watcher route. The one configured
HH applicant credential belongs to the owner profile until per-user OAuth is
designed and approved. A failed vacancy is isolated within its source, with
partial status retained; transport errors are reported by type and HTTP status
without untrusted URLs or response bodies.

The complete original v3.5.1–v4.x product vision remains in canonical root

The two owner proposal Markdown files are reference input and remain untracked.

## Подробные формулировки и критерии

### DEC-001 · Skill Check: только добровольное влияние на сортировку — УТВЕРЖДЕНО 2026-10-18

**Решение владельца:** «Skill Check влияет на сортировку только в отдельном включаемом пользователем режиме, без скрытия вакансий».

**Требования к реализации:**
- По умолчанию влияние Skill Check на вакансии **выключено**. Проверка знаний сама по себе добровольная.
- Только пользователь может включить отдельный переключатель «Учитывать Skill Check при сортировке» и выключить его в любой момент. Включение не должно менять исходный Match Score, фильтры или статусы.
- При включении применяется только **мягкий, объяснимый персональный порядок** среди уже доступных результатов; ничто не исключается и не исчезает из выдачи из-за непройденного/низкого теста, отказа от тестирования или отсутствия оценки.
- Исходный Match Score и основанная на практических упражнениях «готовность/уверенность» отображаются раздельно. Пользователь может просмотреть вакансии в порядке без Skill Check.
- Результаты, ответы и пробелы Skill Check хранятся приватно, не передаются работодателям/рекрутерам и **не** добавляются автоматически в CV, сопроводительные, отклики или экспорт. Отправка таких данных наружу возможна только после отдельного конкретного согласия владельца, если вообще будет поддерживаться.
- Реализация **не начата этим решением**. Включить требование в единый ROADMAP и задачу Codex после согласования остальных пунктов. Разработка/runtime/Git в этом шаге не меняются.

**Ревизия:** согласование Skill Check завершено в части влияния на выдачу.

### DEC-002 · Выдача: подходящие первыми, остальные в отдельной вкладке — УТВЕРЖДЕНО 2026-10-18

**Решение владельца:** «Для AI Job Agent утверждаю вариант A: подходящие вакансии первыми, остальные доступны в отдельной вкладке, включая низкий Match Score и неизвестные условия релокации».

**Требования к реализации:**
- По умолчанию показывать релевантные **Good / Stretch** вакансии первыми, в независимых Career-first и Relocation-first направлениях. Не выдавать выбранную пользователем сортировку за подтверждённую возможность трудоустройства.
- Добавить доступную отдельную вкладку **«Остальные / Ручной просмотр»** со всеми сохранёнными и безопасными для показа результатами ниже порога, а также с неопределённой визовой/релокационной поддержкой или правом найма. Показать низкий score, статус и источник; не переименовывать эти вакансии в Good.
- Для результатов, исключённых настройками до сохранения, обеспечить понятные причины и предусмотренный механизм ручного просмотра *при наличии сохранённых данных*; текущее наличие вкладки не доказывает, что предфильтровые вакансии уже доступны. Не обещать показать записи, которые адаптер не получил и не сохранил.
- В каждой карточке показывать **почему вакансия подходит или не подходит**: роль, географию, зарплату (если известна), ограничения, происхождение и дату, если подтверждены. Разделять `неизвестно` и явные отрицательные ограничения.
- Настоящие юридические ограничения или явный отказ в найме не превращать в «подтверждённо доступно»; спам, небезопасные ссылки и дубликаты по-прежнему должны обрабатываться безопасно. Отдельная ручная вкладка не отменяет защитные правила.
- Не изменять исходные оценку Match Score и hard-policy молча ради количества результатов. **DEC-001** остаётся независимым: добровольный Skill Check может изменять только видимую сортировку в отдельном явно включённом режиме и никогда не исключает вакансии.
- Согласованное поведение относится и к **Web GUI**, и к **Telegram**; реализацию и живую пользовательскую проверку вести отдельными задачами.
- **Реализация не начата этим решением**. GitHub `ROADMAP.md`, ветки и runtime сейчас не изменялись; согласованное требование будет перенесено после завершения поэтапной ревизии.

**Ревизия:** видимость вакансий утверждена. Структура IT/non-IT утверждена отдельно в DEC-003 ниже.

### DEC-003 · Relocation-first: раздельные IT / non-IT направления — УТВЕРЖДЕНО 2026-10-18

**Решение владельца:** «Два независимых направления внутри Relocation-first — IT и non-IT, с отдельными критериями, оценками и настройками, но общим обзором вакансий».

**Требования к реализации:**
- Внутри Relocation-first поддерживать два независимых поисковых трека: **Relocation IT** (DevOps, Linux, инфраструктура и смежные IT-роли) и **Relocation non-IT** (доступная для пользователя работа иных профессий, включая начальные позиции).
- Для каждого трека отдельно настраивать запросы и профессии, источники, географию и приоритеты, критерии соответствия и причины отсева. Не применять требования Kubernetes/Docker/DevOps или другую IT-оценку к non-IT вакансиям.
- Сохранять общий обзор Relocation-first с понятным переключением «Все / IT / non-IT» и независимыми показателями результатов по каждому треку. Не смешивать их оценки так, будто они измеряют одну и ту же квалификацию.
- Риски трудоустройства оценивать **отдельно от профессионального соответствия**: визовая поддержка, право на работу, требования языка, тип контракта, зарплата и другие условия могут быть подтверждены, опровергнуты или неизвестны; неизвестное не равно автоматический отказ.
- По **DEC-002** Good/Stretch показывать первыми, а вакансии ниже порога и неопределённые варианты — в отдельной доступной вкладке «Остальные / Ручной просмотр» с объяснениями; сохранение и просмотр не блокируются низкой оценкой навыков.
- По **DEC-001** Skill Check может лишь добровольно и мягко влиять на порядок вакансий в отдельном переключаемом режиме; результаты тестов приватны, не формируют исключения вакансий.
- Не делать предположение, будто два профиля уже полностью существуют в хранилище: текущая модель Career-first/Relocation-first и общие источники требуют проверки схемы, логики и миграции. Архитектурную реализацию определить при планировании так, чтобы сохранить старые настройки, результаты и историю без дублирования/потерь.
- **Реализация не начата этим согласованием.** В GitHub, рабочие ветки, production-бот и БД изменений этим шагом не внесено. Перенести в канонический ROADMAP только после общей ревизии.

**Ревизия:** стратегия IT / non-IT в релокации утверждена; география согласована отдельно в DEC-004 ниже.

### DEC-004 · Онбординг географии, глобальный поиск и приоритет релокации — УТВЕРЖДЕНО С УСЛОВИЯМИ 2026-10-18

**Уточнённое решение владельца:** вариант **A — «Весь доступный мир + приоритетные страны»**, но не как безусловная заранее заданная конфигурация. При **первом запуске бота новым пользователем** должен открываться мастер настройки: страна и город фактического проживания → дополнительные страны/города для поиска → выбор глобального или ограниченного охвата → приоритеты стран/городов → вакансии с релокационной поддержкой или без неё и приоритет этого признака. Настройки должны быть персональными и изменяемыми. Это дополняет DEC-001–DEC-003.

**Обязательный первоначальный сценарий (Telegram и Web GUI):**
1. Спросить **текущую страну проживания**, затем **текущий город проживания**. Не определять их молча по IP/VPN; текущая локация — самостоятельные поля профиля, она не означает автоматического исключения других рынков.
2. Спросить: **«Добавить ещё страны или города, в которых искать работу?»**. При ответе «да» — дать каталог/поиск с выбором из списка и возможность **ввести страну/город самостоятельно**. При ответе «нет» — продолжить без дополнительных адресов. Нормализовать названия и уточнять неоднозначные топонимы (город + страна/регион), не молча приписывать страну.
3. Предложить **охват поиска**: «весь доступный мир» (вариант A, по умолчанию) или «только выбранные страны/города». Позволять позднее включать/отключать весь мир без потери выбранных пунктов. «Весь мир» — *максимум реально поддерживаемых разрешёнными источниками рынков*, не гарантированный охват всех государств и вакансий.
4. Предложить **упорядочить приоритет стран и городов**: пользователь выбирает, какие сканировать и показывать первыми (например, страна/город №1, №2, №3; прочие — обычный приоритет). Страна проживания не становится первоочередной автоматически без согласия пользователя. Приоритет по умолчанию не является жёстким запретом для других мест.
5. Спросить о **формате переезда**: интересуют вакансии **без необходимости переезда** (местные/удалённые), **с переездом** либо **оба типа**; дать приоритет «с переездом сначала / без переезда сначала / одинаково». **Отдельно** спросить о **релокационной помощи работодателя**: показывать вакансии с помощью переезда/релокационным пакетом, без этой помощи или оба типа; приоритет «с поддержкой сначала / без поддержки сначала / одинаково». Не смешивать необходимость переезда, relocation assistance, visa sponsorship, right-to-work и remote: это разные условия.
6. До первого поиска показать **сводку выбора**: дом, дополнительные рынки, весь мир или выбранные, приоритеты городов/стран, отношение к переезду и релокационной поддержке; дать исправить выбор. Позднее всё редактируется в Settings, не требуя повторного онбординга.

**Поведение поиска и безопасность:**
- Сохранять настройки **для каждого пользователя отдельно**; Career-first, Relocation IT и Relocation non-IT могут наследовать общий географический выбор, но должны иметь собственные переопределения и свои профессиональные фильтры по DEC-003. Для уже существующих пользователей не сбрасывать настройки, историю, заявки или данные — предложить дополнить недостающие поля, сохраняя прежнее.
- Географический приоритет, приоритет переезда и приоритет поддержки **обычно мягко влияют на очередь сбора и сортировку**, но не изменяют исходный Match Score или доступ к вкладке «Остальные». Если пользователь явно выбрал «только выбранные рынки» либо жёсткое условие поддержки, это должно быть показано как **осознанный фильтр**, с доступной информацией об исключениях; отсутствие данных о поддержке не интерпретировать как доказанное «нет».
- Для всех вариантов показывать отдельно **реальные требования работодателя**, **право на работу**, **спонсорство визы**, **релокационный пакет**, и **удалённую работу**. Наличие одного признака не подтверждает остальные.
- Список рынков может быть шире фактически доступных в источниках; интерфейс отмечает «не поддерживается/нет результатов/не проверено», а не выдаёт ложное подтверждение. Соблюдать ограничения источников, бюджет запросов и приватность пользовательского профиля.
- Связь с **DEC-002**: подходящие Good/Stretch первыми, остальные и неизвестные варианты во вкладке ручного просмотра, насколько они действительно сохранены. Связь с **DEC-001**: Skill Check влияет на сортировку только по отдельному opt-in, никогда не скрывает вакансии.

**Граница:** это **утверждённые требования, но ещё не реализация**. Не менять канонический GitHub ROADMAP.md и runtime до окончания поэтапного согласования и подготовки общего change set.

**Ревизия:** согласован onboarding и географическая/релокационная конфигурация.

### DEC-005 · Реальная осуществимость релокации: юридические, финансовые и работодательские условия — УТВЕРЖДЕНО 2026-10-18

**Решение владельца:** «Подробная оценка реальной возможности переезда по работодателю, юридическим требованиям, расходам, зарплате и рискам, с пользовательскими приоритетами. Неизвестное не считать отказом» (вариант A).

**Что должно анализироваться раздельно:**
1. **Работодатель и сама вакансия:** страна фактической работы, удалённость и допустимая страна нахождения, тип контракта, требуемый язык, гражданство/резидентство, необходимое разрешение на работу, наличие или отсутствие явно заявленных sponsorship/relocation/housing. Факты подтверждать ссылкой на конкретное объявление, датой и дословным коротким свидетельством; отсутствие заявления обозначать «не указано».
2. **Юридический маршрут:** возможные категории виз, разрешений на работу и проживания, официальные требования, сроки, ограничения и доступность для конкретного кандидата. Использовать датированные официальные источники; различать «общее правило», «проверено для кандидата», «требует уточнения» и «неизвестно». **Не выдавать текст объявления или статистическую оценку за правовое заключение либо гарантию въезда/найма**.
3. **Финансы и осуществимость:** указанная зарплата с валютой, периодом, gross/net/unknown; жильё, депозит, билеты, документы/сборы, страховка, связь и базовые расходы на первые месяцы. Показывать диапазоны, дату/географию цен и допущения; не придумывать суммы при отсутствии данных. Личный бюджет — приватный, редактируемый и необязательный; отсутствие бюджета не скрывает вакансии.
4. **Риски:** мошеннические признаки, подозрительные платежи/условия, отсутствие данных об организации, сомнительные ссылки, противоречия в объявлениях и юридическая неопределённость. Риск, подозрение и подтверждённый факт не смешивать; давать способ ручной проверки.

**Персональная настройка и итоговая карточка:**
- Отдельные приоритеты факторов: скорость законного переезда, вероятность практической реализации **без численной вероятности оффера**, расходы и запас средств, заработок/потенциал накоплений, релокационная поддержка, безопасность, язык, карьерный рост. Приоритеты — мягкая объяснимая сортировка в рамках DEC-001–004; не менять задним числом базовый Match Score.
- В карточке показывать **профессиональное соответствие**, **условия/поддержку работодателя**, **юридическую проверенность**, **ориентировочную финансовую осуществимость** и **неопределённость** как разные блоки. Давать действия «Сохранить», «Что уточнить у работодателя?», «Открыть официальный источник», «Изменить приоритеты» и «Посмотреть несмотря на риски», если не нарушены защитные ограничения.
- Если источник явно и достоверно запрещает нужный режим найма, указывать конкретное препятствие; если данных нет — «неизвестно / требуется проверка», а **не** отказ. Решение о вакансии остаётся у соискателя. Жёсткий пользовательский фильтр допускается только при сознательном включении с видимыми причинами исключений; опасные/мошеннические источники можно блокировать по отдельным защитным правилам.
- Не делиться бюджетом, положением с документами, правовым статусом, рисками или частными оценками с рекрутерами/работодателями без отдельного конкретного разрешения. Во внешние LLM не отправлять такие поля автоматически.
- Не притворяться, что глобальные законы/цены уже проверены. Проверка официальных источников и живых вакансий — самостоятельная работа с датами и географией; недоступная информация остаётся неизвестной.

**Граница:** DEC-005 — утверждённая спецификация, **не реализация**. Никаких изменений в канонический GitHub `ROADMAP.md`, ветки, production-БД или работающий бот этим согласованием не внесено. Перенос в roadmap после ревизии всех пунктов.

**Ревизия:** оценка релокации согласована.

### DEC-006 · Интеллектуальный поиск: приоритет Telegram и первичных каналов работодателей — УТВЕРЖДЕНО С УСЛОВИЯМИ 2026-10-18

**Решение владельца:** вариант A — автоматический поиск по всем доступным и разрешённым источникам с приоритетом качества, свежести, надёжности и управлением сбоев; у пользователя полный контроль. **Дополнительное обязательное условие:** высокий стартовый приоритет у (1) разрешённых пользователем Telegram-каналов с вакансиями и (2) **официальных первичных каналов работодателей** — страницы Careers/Jobs, проверенные ATS-публикации, публично указанный работодателем способ отклика (включая кадровую почту, если действительно опубликована). Кроме того, бот должен регулярно обнаруживать, проверять и сравнивать **новые, популярные и доказавшие результативность способы поиска работы** по рынкам/странам и учитывать результаты при приоритизации, не полагаясь только на известность ресурса.

**Спецификация:**
- **Discovery и доверие — разные измерения.** Telegram — высокий *стартовый приоритет для обнаружения* новых вакансий и нишевых релокационных сообществ, но пост не является первоисточником компании. Для условий, идентичности вакансии, легальности найма и способа отклика предпочитать проверенную страницу работодателя/ATS, сохраняя ссылку на Telegram-пост как источник обнаружения. Официальный сайт компании — высокий приоритет достоверности, но не гарантирует свежесть или успешный найм.
- **Начальные группы источников:** (1) разрешённые пользователем Telegram job-каналы/подборки; (2) верифицированные employer career pages и ATS/карьерные порталы; (3) доступные профессиональные сети, реферальные программы, специализированные сообщества, рекрутеры/агентства с подтверждаемой репутацией, университетские/локальные программы, официальные государственные службы занятости; (4) общие доски/агрегаторы и другие законные каналы. Это стартовые *ориентиры*, а не жёсткая глобальная сортировка: страна, профиль IT/non-IT, доказанная полезность и пользовательская настройка имеют приоритет.
- **Адаптивные веса:** сочетать пользовательский вес источника (явно заданный — уважать), релевантность именно для Career-first/Relocation IT/Relocation non-IT, свежие уникальные доступные вакансии, подтверждённый первоисточник, долю реальных actionable leads, сохранившиеся отклики/ответы/интервью (только по личным добровольно внесённым данным), дубли, спам, ложные сигналы, задержки, ошибки, разрешённую частоту запросов. Не путать число постов, популярность или рейтинг сервиса с реальным результатом пользователя. При недостатке статистики не делать необоснованных выводов.
- **Новые способы поиска:** поддерживать регулярный research/review источников и подходов: новые проверяемые сайты и ATS, профессиональные/отраслевые сообщества, referral/networking, прямое обращение к работодателю и официальные государственные программы. Проверять дату/регион, доступность, легальность доступа, условия API/robots/договор, применимость для резидента выбранной страны, результаты пилота. Добавление нового источника к активному сбору — после проверок безопасности/согласия, когда оно необходимо; без обхода CAPTCHA, антибота и приватности.
- **Telegram:** только явным образом выбранные/разрешённые пользователем каналы, небольшая пилотная группа с подтверждённым доступом, read-only там, где уместно; никакого автоматического вступления, чтения личных чатов или скрытого мониторинга. Сохранять ссылку/дату поста, канал и ссылки на первоисточник; автоматическая дедупликация вакансий при разных источниках; приоритет прямой проверенной карточке работодателя для окончательного отклика.
- **Официальная почта работодателя:** только верифицированный опубликованный контакт, не добытый из частной переписки/сбора адресов. Бот может подготовить текст, но **не отправляет письма или отклики без подтверждения конкретного адресата и содержания**. Защита от фальшивых карьерных страниц и phishing обязательна.
- **Управление сбоями:** cooldown/backoff, лимиты частоты, диагностические причины, разрешённый fallback и сохранение частичных результатов; не засыпать пользователя одинаковыми тревогами. В GUI показать эффективность по источнику и рынку, пояснить корректировку приоритета и дать включить/выключить источник, зафиксировать вес, запустить разрешённую ручную проверку.
- **Инварианты DEC-001–005:** низкий Score/неизвестное visa/work authorization сами по себе не удаляют вакансию из доступного ручного просмотра; IT/non-IT сравниваются отдельно; личный Skill Check используется только по отдельному переключателю; решения и внешние действия остаются за соискателем.
- **Реализация ещё не начата этим решением.** Это утверждение для общего change set после всей ревизии. Не считать Telegram-каналы уже подключёнными: локальная авторизация, реальные IDs и пилот 2–3 каналов по-прежнему не подтверждены. Канонический GitHub ROADMAP и runtime пока не изменялись.

**Ревизия:** стратегия источников согласована; **следующий пункт — DEC-007:** как именно выбирать, подключать и контролировать Telegram-каналы с точки зрения приватности и автоматизации.

### DEC-007 · Telegram: автоматический мониторинг явно выбранных каналов и папок — УТВЕРЖДЕНО 2026-10-18

**Решение владельца:** «Автоматический мониторинг выбранных и разрешённых Telegram-каналов и папок, с предпросмотром, пользовательским контролем, анализом вакансий и возможностью отключения» (вариант A).

**Требования к реализации:**
1. **Onboarding/подключение:** дать возможность добавить один или несколько каналов, либо ссылку на пользовательскую папку Telegram; показать *предпросмотр* обнаруженных каналов с названием, типом, доступностью, источником и явным статусом доступа. Ссылка или предпросмотр сами по себе не означают, что у бота есть права чтения. Не обещать полного автоматического доступа ко всем чатам папки.
2. **Явный выбор и разрешение:** пользователь утверждает конкретные каналы и профили для мониторинга (Career-first, Relocation IT, Relocation non-IT); все вновь обнаруженные каналы по умолчанию **выключены**. Можно назначать приоритет, приостанавливать/включать отдельный канал и отозвать доступ. Доступ и настройки — персональные.
3. **Разделить режимы доступа:** Bot API считывает только доступные и разрешённые ему публикации; для личных папок и каналов, недоступных Bot API, возможен отдельный **опциональный локально авторизованный read-only MTProto-клиент**, который проверяет доступность каждого выбранного канала. Логин/код/2FA/файлы сессии остаются на компьютере пользователя, не публикуются и не передаются в GitHub/CI. Никакого автоматического вступления, подписок, отправки сообщений, чтения личных диалогов или скрытого сканирования аккаунта.
4. **Обработка:** только новые доступные посты и допустимый контролируемый catch-up; сохранять ссылку, канал, ID поста, дату, источник обнаружения, извлечённые факты вакансии, объяснимую оценку по нужным профилям и дедупликацию с другими сайтами. Рекламу, чужие резюме, спам и потенциальный скам помечать отдельно. Официальную страницу работодателя/ATS предпочитать при проверке фактов и способа отклика, но не терять Telegram как источник обнаружения (DEC-006).
5. **UX и управление:** в Telegram и Web GUI показывать список выбранных каналов, разрешения, последнее успешное чтение, количество *уникальных и полезных* вакансий, ошибки, фильтрацию и причины. Есть «Проверить доступ», «Прочитать новые», «Приостановить», «Отключить», «Удалить локальные данные/сессию» после подтверждения. Пользователь выбирает частоту из безопасного диапазона; ограничения платформы и backoff соблюдать.
6. **Надёжность и честные статусы:** повторные попытки безопасны, курсоры сохраняются приватно, повторное чтение не создаёт дубли; статус «не проверено / нет доступа / работает / ошибается» отражает факты. Технические сбои не превращаются в регулярный спам-отчёт и не останавливают другие источники.
7. **Реальная проверка до расширения:** проверить локальную авторизацию и доступ к 2–3 выбранным каналам, затем пропустить хотя бы один *реальный* свежий пост через единый pipeline с указанием источника и оценкой качества. После успешного пилота разрешить подключение остальных по выбору пользователя. Имеющаяся папка из 21 наименования **не подтверждает** их ID, типы, право читать или фактический сбор.
8. **Общие ограничения:** DEC-001–006 остаются действующими; Skill Check приватен, IT/non-IT независимы, неотобранные вакансии доступны для ручного просмотра согласно DEC-002, никакой автоматической отправки откликов и сообщений.

**Статус:** это **утверждённая спецификация**, а не новый коммит или включение мониторинга. Уже реализованный Telegram Folder Watcher следует переиспользовать. GitHub roadmap, runtime, Bot API/MTProto-сессии и production-БД при согласовании не менялись. Перенести решение в канонический ROADMAP после завершения общей ревизии.

**Ревизия:** режим Telegram утверждён. **Следующий пункт DEC-008 — профиль кандидата, навыки и резюме (Candidate Facts/CV), его конфиденциальность и редактирование.**

### DEC-008 · Интеллектуальный профиль, подтверждённые факты и несколько CV — УТВЕРЖДЕНО 2026-10-18

**Решение владельца:** «Полноценный интеллектуальный профиль кандидата с проверяемыми фактами, разделением коммерческого опыта, проектов и обучения, несколькими редактируемыми RU/EN резюме, пользовательским подтверждением изменений и приватным Skill Check» (вариант A).

**Требования к реализации:**
1. **Единый персональный профиль кандидата:** ввод вручную и импорт согласованных резюме PDF/DOCX/TXT; навыки, коммерческий опыт, проекты/homelab, обучение, образование, языки, карьерные и релокационные пожелания, ограничения. Показывать источник, дату, подтверждённость и возможность исправить или убрать каждое существенное утверждение. Не считать извлечённый текст автоматически проверенным фактом.
2. **Строгое разделение опыта:** коммерческая работа ≠ самостоятельный проект ≠ учебная практика ≠ предположение модели. Проверка Skill Check подтверждает лишь результат упражнения, а не коммерческий стаж. Никаких придуманных работодателей, длительности работы, production-инцидентов, сертификатов или владения технологией.
3. **Несколько независимых CV:** версии RU/EN и по направлениям DevOps/Infrastructure/SRE, системное администрирование, Security, Relocation IT/non-IT и конкретной вакансии. Пользователь может дублировать, сравнить, редактировать, экспортировать и выбрать нужную версию; один общий базовый набор одобренных Candidate Facts. Не смешивать non-IT и технические критерии, сохраняя возможность указать переносимые навыки.
4. **Помощь с адаптацией:** предлагать реальное соответствие требованиям вакансии, недостающие сведения, структурные/ATS улучшения, несколько осторожных формулировок и локальный diff. Никаких обещаний «100% прохождения ATS» или искусственного повышения навыков. Изменения и содержимое CV **только после явного подтверждения владельца**; предыдущие версии и происхождение утверждений доступны для сравнения/отката.
5. **Приватность и контроль:** резюме, кандидатские факты, тесты, ответы, пробелы, заметки и версии — личные данные пользователя; не выдавать работодателям, рекрутерам или в общедоступные логи, GitHub, отчёты и CI без отдельного осознанного подтверждения содержания, адресата и канала. Учитывать внешние AI API как возможную передачу данных отдельному провайдеру, показывать выбор/последствия и предусмотреть приватный режим. Не делать автоматических внешних откликов.
6. **Связь со Skill Check (DEC-001):** результаты добровольной проверки знаний остаются частными, могут порождать рекомендации по обучению или **предложения** о корректировке профиля, но не переписывают Candidate Facts/CV автоматически. Влияние на сортировку вакансий выключено по умолчанию; при включении — только объяснимый мягкий порядок, без скрытия вакансий или изменения исходного Match Score.
7. **Реализация без переписывания основы:** переиспользовать уже существующие Candidate Facts, импорт, `/compare`, `/resumediff`, подготовленные пакеты и Web CV; проверить различие «в коде / тестах / живой приёмке» и закрывать только реальные пробелы. Изменение схемы или миграция — только после отдельной оценки сохранности данных.

**Статус:** это утверждённая спецификация для переноса в канонический `ROADMAP.md` после общей ревизии, **не** новый коммит, не изменение существующих записей в PostgreSQL и не выкладка GUI. Рабочий runtime не менялся.

**Ревизия:** профиль и CV утверждены. **Следующий пункт DEC-009 — формат добровольной Skill Check, практики собеседования и обратной связи.**

### DEC-009 · Адаптивный добровольный AI Skill Check и подготовка к собеседованиям — УТВЕРЖДЕНО 2026-10-18

**Решение владельца:** «Адаптивный AI Skill Check с общей и вакансионной проверкой, выбором длительности и сложности, практическими заданиями, вопросами, диагностикой ошибок, симуляцией собеседования и персональной обратной связью» (вариант A).

**Требования к реализации:**
1. **Только по выбору пользователя:** начинать проверку вручную из профиля, конкретной вакансии или раздела подготовки; не требовать теста для просмотра, сохранения, сравнения вакансий и отправки ручного отклика. Можно пропустить, остановить, повторить и удалить результат.
2. **Два контекста:** общая проверка по навыкам и профессии из подтверждённого Candidate Profile либо проверка под конкретную вакансию с указанием её обязательных/желательных требований; источник требований и их неопределённость видны. Не переносить IT-критерии на non-IT роли.
3. **Настраиваемая сессия:** длительность 5, 15 или 30 минут и выбранная сложность; разумная комбинация вопросов, прикладных задач, troubleshooting/диагностики ошибок, объяснения решений и симуляции интервью. Адаптация следующего задания зависит от предыдущего ответа и выбранной цели, но не от скрытого «профиля пригодности» работодателя. Возможны ответ «не знаю», подсказка, пропуск, приостановка.
4. **Персональная обратная связь:** что кандидат продемонстрировал, что требует проверки, ошибки с объяснениями, точечный план практики/обучения, предложение повторного упражнения. Оценивать ход решения и контекст; не выдавать результаты теста за объективное подтверждение стажа, сертификата или вероятность оффера. Отображать дату, метод проверки и неопределённость.
5. **Изоляция от оценки вакансий:** исходный Match Score, статус Good/Stretch, фильтры и видимость вакансий не меняются. По DEC-001 можно отдельно **включить** лишь мягкое и объяснимое влияние Skill Check на порядок уже доступных вакансий; по умолчанию оно **выключено**. Без теста пользователь получает такую же полную выдачу.
6. **Приватность на стороне соискателя:** ответы, сессии, оценки, пробелы и рекомендации доступны только владельцу; не уходят работодателям, рекрутерам, в отклики, CV, письма и публичные отчёты автоматически. Для передачи ответа внешнему AI-провайдеру — понятный выбор и согласие с режимом обработки; предусмотреть локальный/безвнешний вариант, где он технически доступен. Результаты не меняют Candidate Facts или CV без отдельного подтверждения пользователя (DEC-008).
7. **Переиспользование кода:** расширять уже существующие `/interview`, skill comparison, Candidate Facts, Web GUI вместо создания второго несвязанного тестового продукта. Ранее реализованные наборы сценариев — база; полноценный диалог, оценка ответов и адаптивное продолжение требуют отдельной реализации и живой приёмки.

**Граница:** DEC-009 — утверждённое требование в документе согласования, **не** реализованный интерактивный AI Skill Check. Канонический `ROADMAP.md` на GitHub, runtime, PostgreSQL и Codex этим шагом не изменяются. Перенести в единый roadmap после согласования остальных решений.

**Ревизия:** формат Skill Check и Interview Agent согласован. **Следующий согласованный пункт DEC-010 — AI Application Assistant.**

### DEC-010 · AI Application Assistant: индивидуальная подготовка, утверждённая отправка и сопровождение — УТВЕРЖДЕНО 2026-10-18

**Решение владельца:** «AI Application Assistant готовит индивидуальные резюме и письма, находит официальные каналы, отправляет только после подтверждения каждой конкретной заявки пользователем через разрешённую интеграцию, иначе помогает отправить вручную, отслеживает HR и сроки» (вариант A).

**Требования к реализации:**
1. **Подготовка под конкретную вакансию:** использовать выбранное и подтверждённое RU/EN резюме, проверенные Candidate Facts, оригинальную публикацию и условия роли; предлагать обоснованные правки CV и сопроводительного письма, вопросы работодателю. Не придумывать опыт, образование, зарплату, визу или гарантии результата. Не раскрывать приватные Skill Check/оценки по умолчанию.
2. **Проверяемый способ отклика:** искать официальный карьерный сайт/ATS или публично подтверждённый контакт работодателя; указывать источник, уровень уверенности, риски подмены адреса и, по возможности, различать агрегатор и оригинал. Не считать найденную почту разрешением на автоматическую рассылку.
3. **Обязательное согласие на каждую отправку:** до внешнего действия показать получателя/канал, конкретную вакансию, текст письма, резюме, вложения, поля формы, раскрываемые персональные данные и ссылку; пользователь явно подтверждает **именно эту** заявку. Никаких пакетных, фоновых, повторных, скрытых или «по умолчанию разрешённых» откликов. Даже ранее утверждённый черновик не разрешает отправку по другой вакансии или после существенного изменения содержимого.
4. **Отправка только допустимым способом:** если доступна разрешённая интеграция и явное подтверждение — выполнить однократное действие с журналом результата и защитой от дублей. Если способ недоступен, запрещён площадкой или требует непредусмотренного обхода — открыть официальный канал и помочь отправить **вручную**, без обхода CAPTCHA, антибот-систем и ограничений работодателя.
5. **Application CRM и сопровождение:** фиксировать сохранение, подготовку, утверждение, отправку, подтверждение приёма, ответ HR, тестовое задание, интервью, отказ, оффер и закрытие; отличать подтверждённое событие от ручной отметки пользователя. Хранить неизменяемую копию отправленного пакета и историю изменений, показывать дедлайны/напоминания и предлагать follow-up, но не рассылать его без отдельного подтверждения содержания и адресата.
6. **Защита интересов соискателя:** предупреждать о подозрительных вакансий/реквизитах, скрытых условиях, оплате за трудоустройство, сомнительных тестовых заданиях и рисках персональных данных; учитывать переговоры о зарплате/релокации, но не принимать предложение/отказ вместо пользователя. Ответы на вопросы о гражданстве, визе, разрешении на работу и других чувствительных условиях — только после пользовательского просмотра и согласия.
7. **Использовать готовую основу:** переиспользовать существующие `/prepare`, Applications, замороженные пакеты, Candidate Facts и Web GUI. Подготовка, история и ручные статусы частично уже реализованы и протестированы; внешняя отправка, полноценное отслеживание HR и разрешённые интеграции требуют отдельной проверки. **Утверждение спецификации не означает, что отправка уже работает.**
8. **Связь с DEC-001–009:** пользователь контролирует каждую заявку; результаты Skill Check приватны; для IT/non-IT выбирается корректный CV; неопределённость права на работу и релокационных условий не превращается в выдуманную гарантию.

**Граница:** DEC-010 внесён только в документ согласования. Канонический `ROADMAP.md`, GitHub, Codex, production runtime, PostgreSQL и Docker volumes не изменены этим решением. После обсуждения всех пунктов перенести в единый roadmap с отдельными критериями приемки и release gates.

**Ревизия:** workflow откликов утверждён. **Следующий пункт DEC-011 — какой интерфейс является основным: Web GUI, Telegram или равноправные интерфейсы, и как организовать ежедневный workflow/уведомления.**

### DEC-011 · Web GUI как основной центр управления, Telegram как мобильный помощник — УТВЕРЖДЕНО 2026-10-18

**Решение владельца:** «Web GUI — основной центр управления AI Job Agent, Telegram — полноценный мобильный помощник для уведомлений, поиска, просмотра и быстрых действий. Данные общие и синхронизированы» (вариант A).

**Требования к реализации:**
1. **Web GUI — основной интерфейс:** понятная главная страница с последними результатами поиска и следующими действиями; разделы Search, Jobs/Review, Profiles, Sources, Relocation IT/non-IT, CV, Skill Check/Interview, Applications, настройки, журнал и отдельная Diagnostics. Первичную настройку страны/города, географических приоритетов и интереса к релокации выполнить по DEC-004, позже разрешить редактирование. Не превращать GUI в технический терминал с сырыми JSON/logs.
2. **Telegram — повседневная мобильная работа:** краткие и управляемые уведомления о подходящих вакансиях, ручной просмотр Good/Stretch и «Остальных» (DEC-002), карточки с источником и причинами, сохранение/пропуск, быстрый запуск и статус поиска, доступ к очередям, подготовленным пакетам и статусам отклика. Длинные документы и сложные формы могут вести в Web GUI, но не должны мешать базовым быстрым действиям.
3. **Единые данные и правила:** оба интерфейса используют одну серверную модель профиля пользователя, Search Profiles, Candidate Facts/CV, вакансий, отметок, заявок и пользовательских согласий; записи синхронизируются по факту сохранения. Не заводить конкурирующие копии данных или два независимых алгоритма scoring. Отображать время актуальности и обрабатывать устаревшие состояния.
4. **Никаких конфликтов и повторных действий:** Web, Telegram и scheduler согласуют параллельные сканирования, дедупликацию, повторную подготовку откликов и статусы. Подтверждение конкретной внешней отправки обязательно независимо от того, в каком интерфейсе её инициировали (DEC-010). Не отправлять заявки из-за нажатия на просмотр, сохранение или подготовку.
5. **Удобство и доступность:** русскоязычный интерфейс по умолчанию, в дальнейшем опциональная локализация; адаптация под ПК и телефон, понятная навигация, фильтры, действия на карточках, доступность ошибок и состояния загрузки. Web GUI как основной центр не означает отказ от работающего Telegram runtime.
6. **Уведомления под контролем соискателя:** настраивать каналы, частоту, тишину, приоритет, сводки и предупреждения; группировать похожие сетевые ошибки и отправлять технические подробности в Diagnostics. Приоритет — новые полезные вакансии и события отклика, а не поток служебных ошибок. Не заявлять о "новых" вакансиях при повторной доставке.
7. **Изоляция и безопасность:** owner-only доступ, авторизация/сессии/CSRF, приватный localhost-доступ Web GUI на первом этапе, без публичной публикации без отдельно согласованной защиты; у будущих пользователей отдельные данные и настройки. Приватные результаты Skill Check не попадут к работодателю из Web или Telegram (DEC-001, DEC-009).
8. **Текущее состояние не путать с готовностью:** реализация базовых страниц и действия уже присутствуют в PR #50/#51, однако живой Web browser acceptance и развёртывание в runtime остаются отдельными release gates. Новые страницы Skill Check/полная CRM — требования для следующих этапов, не якобы готовые функции. Приоритет — запуск и ежедневное использование существующего GUI с реальными данными, затем развитие по согласованному roadmap.

**Граница:** DEC-011 пока утверждён **только в этом документе согласования**. GitHub `ROADMAP.md`, локальный Codex, production PostgreSQL и работающий бот не изменяются этим шагом.

**Ревизия:** роли Web GUI и Telegram утверждены. **Следующий пункт DEC-012 — AI Router / AI Stack Watch: выбор моделей, лимиты, стоимость, ресурсы и конфиденциальность.**


### DEC-012 · Интеллектуальный AI Router и AI Stack Watch — УТВЕРЖДЕНО 2026-10-18

**Решение владельца:** «Интеллектуальный AI Router с автоматическим выбором разрешённых моделей по качеству, стоимости, сложности задачи, лимитам и ресурсам, с локальным режимом для приватных данных и постоянным AI Stack Watch новых моделей. Все расходы и передачи данных контролируются пользователем» (вариант A).

**Требования к реализации:**
1. **Автоматический выбор в рамках разрешённого:** выбирать модель и способ исполнения для конкретной задачи (поиск/нормализация, CV и письма, Skill Check/Interview, релокационная аналитика, объяснения). Простые детерминированные действия выполнять без LLM; быстрые/недорогие модели — для типовых задач; более сильные — только когда измеренная польза оправдывает задержку и цену.
2. **Настройки под пользователя:** список доступных и разрешённых провайдеров/моделей, ручное переопределение, ограничения расходов за запрос/день/месяц, предпочтения качества/скорости, допустимые внешние передачи и режимы приватности. По умолчанию — без несанкционированных платных вызовов и внешней передачи чувствительных данных. Исчерпание лимита не оправдывает обход ограничений или скрытую смену провайдера.
3. **Учитывать реальные ресурсы:** RAM, VRAM, CPU/GPU, загрузку устройства, контекст и задержку — только по проверенным локальным показателям и возможностям исполнителя. При недостатке ресурсов использовать разрешённый fallback или честно сообщать, что операция недоступна; не выдавать тестовый/локальный режим за реально развёрнутый.
4. **Локальный приватный режим:** возможность обрабатывать резюме, Candidate Facts, ответы Skill Check и другую чувствительную информацию локально, если есть подходящая модель и ресурсы. В строгом локальном режиме не отправлять промпты, содержимое, вложения и результаты внешним провайдерам; отсутствие локальной возможности явно показывать, а не обходить настройку.
5. **Прозрачность и контроль:** показывать выбранную модель/маршрут, причину выбора, оценку и фактические расходы/токены там, где доступны официальные данные, задержку и переключения. Разрешение на передачу конкретных категорий данных и платные операции — явно контролируемое. Недоступные API-лимиты не угадывать и не заявлять, что бот может читать приватные лимиты ChatGPT/Codex без соответствующего поддерживаемого доступа.
6. **AI Stack Watch:** регулярно выявлять и сравнивать новые open-source/open-weight, флагманские, экспериментальные и специализированные модели, лицензии, доступность, качество для задач бота, требования VRAM/RAM, скорость, цену и ограничения API. Отделять новость/анонс от независимо проверенных результатов; не менять production-модели автоматически по рекламному рейтингу. Новую модель допускать после тестов на репрезентативных задачах, приватность, затраты, fallback и одобрение политики пользователя.
7. **Не ломать интересы соискателя:** никакая модель не получает право самостоятельно отправлять CV или отклики, менять Candidate Facts без подтверждения, раскрывать Skill Check работодателю или превращать неподтверждённую возможность переезда в гарантию. Сохраняются DEC-001–011, пользовательские границы расходов и передачи данных.
8. **Границы реализации:** это утверждённая продуктовая спецификация, **не** доказательство существования готового AI Router, локального inference или непрерывного мониторинга моделей. Сначала измерить доступные маршруты и ресурсы, затем поэтапно интегрировать в существующую архитектуру с тестами и отдельными критериями готовности.

**Статус фиксации:** решение внесено в настоящий документ согласования. Канонический GitHub `ROADMAP.md`, локальный Codex, runtime, production PostgreSQL и Docker volumes этим шагом **не менялись**. Переносить утверждённые решения в единый roadmap после окончания ревизии.


### DEC-013 · Privacy-first: данные принадлежат и подконтрольны пользователю — УТВЕРЖДЕНО 2026-10-18

**Решение владельца:** «Privacy-first, полная пользовательская собственность и контроль данных, локальное хранение по умолчанию, внешняя передача только по разрешению, безопасные резервные копии, экспорт, удаление и аудит действий» (вариант A).

**Требования к реализации:**
1. **Локальное хранение по умолчанию:** персональные данные (Candidate Facts, версии резюме, Skill Check, профили и приоритеты поиска, история вакансий/заявок, релокационные заметки, контакты и документы) хранятся в инфраструктуре, контролируемой пользователем. Указать, какие данные и где реально хранятся; не объявлять существующий runtime уже полностью соответствующим новой политике без проверки.
2. **Разрешения на внешнюю передачу:** пользователь выбирает интеграции и категории данных, допускаемые к передаче. Перед передачей отображать получателя, назначение, категории, объём и последствия; внешние LLM/API и внешняя синхронизация — только в пределах явных разрешений. Отдельное подтверждение каждой отправки вакансии/резюме/письма работодателю обязательно по DEC-010. Настройки маршрутизации моделей из DEC-012 не обходят запреты.
3. **Изоляция и доступ:** подтверждённая owner-authenticated модель, разграничение по пользователю, защита сессий, CSRF и конфиденциальных запросов; безопасное хранение токенов/секретов, по принципу минимальных прав. Не добавлять пользовательские данные, ключи, Telegram-сессии, приватные резюме и дампы в публичный GitHub или CI-логи.
4. **Просмотр, исправление и переносимость:** UI и документированный экспорт данных пользователя в переносимых форматах, с понятным составом экспорта и выбором включаемых разделов. Исправление/удаление Candidate Facts, профиля, устаревших документов и результатов Skill Check — по подтверждённому запросу пользователя; не путать скрытие в интерфейсе с удалением из хранилища.
5. **Удаление и сроки хранения:** реализовать понятную политику удаления из активной БД, файлов и производных индексов/кэшей, а для резервных копий — конкретный срок хранения, условия шифрования и порядок истечения срока либо контролируемого удаления. Не обещать мгновенного удаления уже созданных архивных или внешних копий, если такое удаление технологически не доказано. Учитывать историю откликов и доказательства отправки, чтобы удаление одного объекта не приводило к незаметной порче другого.
6. **Резервные копии и восстановление:** ограниченные права, защищённое хранение, подходящее шифрование конфиденциальных копий, проверка восстановления на изолированном экземпляре, контролируемое время хранения и отсутствие секретов в логах. Для изменения production — отдельный backup/rollback gate.

### DEC-014 · Единый roadmap, контекстная синхронизация и экономное управление Codex — УТВЕРЖДЕНО 2026-10-18

**Решение владельца:** «Единый канонический ROADMAP.md, журнал решений, актуальный HANDOFF, синхронизация значимых изменений из доступных чатов, GitHub и Codex с источником, датой и проверкой, без дублирования задач. Codex Main автономно работает с экономным использованием Fast/Deep и Git checkpoints. Реальная пользовательская ценность в приоритете» (вариант A).

**Требования к реализации и процессу:**
1. **Один канонический план:** корневой `ROADMAP.md` — единственный действующий план продукта; отдельный `docs/PROJECT_OS/DECISIONS.md` — журнал утверждённых пользователем решений и их последующих изменений; `docs/PROJECT_OS/HANDOFF.md` — короткая, однозначная текущая точка продолжения. `BRIEF`, `TASKS` и `DEVELOPMENT_LOG` поддерживают план, но не создают конкурирующие очереди и приоритеты. История должна сохраняться без удаления подтверждённых сведений и без длинных повторов в актуальной части.
2. **Синхронизация только доступного:** периодически при разрешённом запуске собирать *значимые* сведения из доступных чатов ChatGPT (включая карьеру, релокацию, обучение и AI Stack Watch), подключённого GitHub, разрешённых файлов проекта и журналов/артефактов Codex. Не утверждать, что есть автоматический фоновый доступ ко всем прежним чатам, локальному терминалу или личным файлам, если такого доступа фактически нет. Отсутствующий источник помечать как недоступный; не восполнять его догадками.
3. **Компактные change sets:** для каждого изменения указывать источник, дату события/наблюдения, подтверждение владельца и уровень уверенности, затронутый компонент, действие (`merge / extend / conflict / new`), влияние на активные требования, статус реализации и ожидаемый результат. Устаревшие или противоречащие сведения не заменяют более поздние подтверждённые решения; конфликт выносится пользователю до изменения политики или ограничений.
4. **Защита от дублирования:** прежде чем планировать или писать код, сверять задачу с `ROADMAP`, `DECISIONS`, текущим `HANDOFF`, кодом, тестами и смерженными PR. Разделять `planned / implemented / tested / owner-accepted live / released`, не начинать заново уже реализованный GUI/Watcher/Matching. Для каждого активного пункта — один идентификатор, исполнитель, причина приоритета, критерий приёмки и проверяемое доказательство.
5. **Пользовательская ценность как верхний приоритет:** работающий поиск вакансий, релокационная пригодность, ясные результаты, CV/отклики и ежедневный Web GUI важнее бесконечных тестовых переработок и косметического рефакторинга. Достаточные небольшие регрессии обязательны по инкременту; полный CI, изолированный PostgreSQL, backup/rollback и браузерная приёмка — по соответствующим release gates. Нельзя выдавать зелёные тесты за проверенную пользователем полезность.
6. **Codex Main как координатор:** один основной Main. Простые и локальные задачи он решает сам; экономный Fast и глубокий Deep подключаются только если ожидаемая польза превышает накладные расходы, преимущественно по одному, с явным и ограниченным контекстом. Не расходовать лимиты на многократные аудиты или переписывание истории без фактической потребности.
7. **Git checkpoint и безопасное продолжение:** фиксировать законченные проверенные изменения логическими коммитами, проверять diff/secret scan, синхронизировать только правильную рабочую ветку; вести краткий актуальный HANDOFF с точным HEAD, сделанным, проверенным, оставшимся и следующим шагом. Не путать dev worktree с `/mnt/Storage/AI-Job-Bot/repo` runtime. Никогда не применять `reset/clean`, не менять production PostgreSQL/volumes, не публиковать секреты и не отправлять заявки без предусмотренного разрешения и релизных условий.
8. **Автономность с границами:** Codex может самостоятельно реализовывать уже согласованный локальный технический этап, исправлять регрессии и создавать checkpoint/PR согласно согласованным правам; изменение продуктовой политики, допущений о переезде, обработка чувствительных данных и реальные действия от имени соискателя требуют указанного подтверждения. Ограничения доступных инструментов/лимитов не маскировать обещаниями непрерывной работы.

Возвращаться к владельцу за UX-приёмкой Web GUI, полезности вакансий и условиями откликов, а не только за подтверждением количества тестов.

**Статус фиксации:** это утверждённый организационный порядок, **не** изменение удалённого `ROADMAP.md` и не автоматическое включение фоновой синхронизации. Решение добавлено только в документ согласования; GitHub, локальная сессия Codex, runtime и БД на этом шаге не менялись. Перенести в канонические файлы после завершения ревизии и итогового согласования.

### DEC-015 · Поэтапные безопасные релизы и пользовательская приёмка — УТВЕРЖДЕНО 2026-10-18
